# V0.1 Local-First Host & Integration Readiness

**Status:** Planned after R1-C14 completion.

**Baseline:** PR #158 merge `e428c1f33e11fb535efb17f66ab9f2ce7dbef3e9`; C14.1–C14.9 are complete. Execution/recovery internals remain frozen unless this milestone proves a concrete invariant violation.

## Objective

Demonstrate that QuantX's existing application, persistence, reconciliation, and adapter components can be composed and operated through a documented, reproducible local process lifecycle. This is an integration-readiness milestone, not a greenfield runtime, a feature expansion, or a declaration that production LIVE trading is certified.

## Why this is next

- The implementation build order says the v0.1 release gate is not yet declared complete and treats the CLI/minimal operational boundary as future work.
- `ProductionRuntime` currently owns SQLite resources and composes recovery-backed startup, while `ApplicationRuntime` is a one-shot recovery hook—not a service loop or executable host by itself.
- The execution audit's stated remaining direction is stack integration and host/deployment work, with further execution/recovery restructuring discouraged absent a new invariant violation.
- R1-C14 now proves deterministic dataset ingestion through persistence, research provenance, a completed research run, and reopen verification. A new data/provenance subsystem is not the next dependency.

## Scope

### Slice 1 — Acceptance-criteria audit

1. Locate the canonical v0.1 acceptance-criteria document and repair any stale links or conflicting status text.
2. Map each criterion to the exact implementation module, regression test, and current validation evidence.
3. Separate proven behavior, unproven integration, deployment prerequisites, and explicitly deferred capabilities.
4. Return a gap table before implementation; do not recreate existing abstractions.

### Slice 2 — Minimal host composition, only if the audit proves a gap

- Inspect existing package scripts, host composition, `ProductionRuntime`, Dhan host wiring, configuration, and resource ownership.
- Define one explicit local invocation and explicit configuration contract.
- Preserve account/connection/broker identity; choose no defaults and keep secrets/vendor SDK construction out of the core.
- Require pending LIVE recovery to finish before reporting execution readiness.
- Ensure a startup failure cannot leave the host in a ready state, and process-owned resources close on normal and exceptional exits.

### Slice 3 — Offline integration proof

Use SQLite and in-memory/fake adapters only. Cover configuration validation, startup and recovery success/failure, pending/failed recovery reporting, fail-closed readiness, shutdown/close semantics, and durable restart behavior. Startup recovery must not expose or call broker submission. Do not claim real-broker end-to-end behavior.

### Slice 4 — Release evidence

Document the local setup and run commands, configuration inputs, readiness semantics, shutdown, supported surfaces, known limitations, and exact local validation output. Evaluate v0.1 acceptance criteria only after the evidence map is complete.

## Exit criteria

- Every release criterion is mapped to code/test/evidence or an explicit blocker.
- The supported local lifecycle is repeatable from a clean checkout using documented commands, or a reasoned decision documents why an executable host is outside v0.1 scope.
- Recovery runs before execution readiness; recovery failure fails closed.
- No implicit account, broker connection, credential, or provider fallback exists.
- Process-owned SQLite/resources close on success and failure; restart behavior is tested where relevant.
- Focused tests, full pytest, configured Ruff/mypy checks, and `git diff --check` pass locally at the exact final commit.
- Documentation states clearly that local integration tests do not certify real-broker or production LIVE readiness.

## Non-goals

- UI, AI/LLM execution, strategy marketplace, or broad strategy platform
- distributed workers, cloud infrastructure, streaming, generic scheduler, or generic job orchestration
- broad broker/venue expansion
- new reconciliation, runtime, router, registry, idempotency, or provenance abstractions without a demonstrated ownership gap
- live order submission in tests or automatic live-trading enablement

## Working rule

Start with the audit and gap table. Make the smallest justified follow-on branch only after exact failing/missing criteria are identified. Implementation and validation run locally; GitHub Actions is not a repository gate while billing is disabled.
