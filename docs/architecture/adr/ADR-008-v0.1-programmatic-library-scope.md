# ADR-008: v0.1 Ships as a Programmatic Local-First Library; CLI Deferred

Status: Accepted

## Context

QuantX is trading infrastructure and a set of contracts, not a complete
opinionated product. No command-line interface, `__main__.py` module,
`console_scripts`/`entry-points` declaration, service manifest, or generic
process entrypoint exists anywhere in the repository: `src/` contains no CLI
framework import and no `sys.argv` handling, `pyproject.toml` declares no
scripts, and the only `if __name__` guards are test helpers under `scripts/`.
The vision, the v0.1 build order ("CLI and minimal API boundary — future
platform surface"), the production-host boundary, and the roadmap readiness
notes all describe executable surfaces as future work — but
`docs/roadmap/feature-priorities.md` still lists CLI under "V0.1 priority",
so the documentation contains a real scope conflict that the v0.1 release
gate (HOST-01) cannot pass without a decision.

Meanwhile the programmatic composition surface is implemented, tested, and
stable: `DhanHostConfig` carries every deployment input explicitly with
fail-closed validation, `build_dhan_host_runtime()` composes transport,
adapter, market-data access, registry, and recovery-backed startup with no
defaults, and `DhanHostRuntime.start()` runs mandatory pending recovery
before reporting readiness while `close()` (also a context manager) shuts
persistence and transport down deterministically. Recovery never submits
broker orders.

## Decision

Scope v0.1 as a **programmatic local-first library** whose supported
bootstrap contract is:

- configure: `DhanHostConfig` (`src/quantx/plugins/dhan/host.py`) with an
  explicit database path, account/connection identity, market context,
  instruments, timeouts, and exactly one of credentials or transport;
- compose: `build_dhan_host_runtime(config)` — no default account,
  connection, broker, credential, or provider fallback;
- run: `DhanHostRuntime.start(checked_at=...)`, which completes pending
  recovery before `started` becomes true and propagates startup failure
  without reporting readiness;
- shut down: `DhanHostRuntime.close()` (or the context manager), which
  closes persistence first and then the transport.

Defer the CLI — and larger user-facing platform surfaces (service host,
containers, schedulers) — to a later milestone. A programmatic API is not a
claim that a CLI or generic service host exists.

## Consequences

Positive:

- the v0.1 release gate can close on evidence instead of waiting for an
  unbuilt product surface;
- the shipped contract matches what the 1,483-test suite actually proves,
  including the host-composed restart regression;
- no new runtime code, dependencies, or operational semantics are required.

Negative:

- v0.1 consumers must write a small Python bootstrap instead of invoking a
  command; operator ergonomics arrive with the later CLI milestone;
- the deferred CLI must be designed against this same bootstrap contract
  when its milestone arrives, not as a parallel composition path.

## Alternatives rejected

- Building a minimal CLI for v0.1: adds an unrequested product surface and
  a second composition path with no user need evidenced; the roadmap
  sequencing explicitly defers it.
- Leaving HOST-01 as GAP while everything else passes: keeps the gate open
  with no remaining technical blocker, contradicting the evidence.

## Revisit when

A concrete operator need justifies a CLI or service host; design it as a
thin wrapper over this bootstrap contract.
