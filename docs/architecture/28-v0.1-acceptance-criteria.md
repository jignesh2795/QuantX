# QuantX v0.1 Acceptance Criteria

QuantX v0.1 is complete only when the following architectural and functional invariants are satisfied.

## Core

- Domain core has no direct dependency on a specific broker, UI, AI provider, or vendor SDK.
- Orders, fills, positions, portfolios, risk decisions, and events have explicit contracts.
- Money uses exact decimal semantics where financial precision requires it.
- Time is explicit and testable; simulation does not depend on wall-clock time.
- Live commands are idempotency-aware.

## Execution environments

- The same strategy/domain semantics can operate in backtest, replay, paper, and live contexts.
- Execution environment changes are implemented primarily through ports/adapters, clocks, data sources, and execution venues.
- Paper trading is a first-class execution mode.
- Recovery always reconciles broker state before resuming live trading.

## Indian-market foundation

- Instruments and contracts support equity, futures, and options as first-class concepts.
- Expiry, strike, option type, lot size, tick size, multiplier, trading session, fees/charges, and margin-related metadata are representable without vendor-specific fields in the domain core.
- Market calendars are explicit and versionable.
- Corporate-action handling is represented in the data/accounting architecture.

## Plugin architecture

- Broker, data, strategy, analytics, research, notification, and AI extensions can be added through declared interfaces.
- Plugins declare compatibility, capabilities, dependencies, permissions, and version.
- Core trading code does not import a specific plugin implementation.
- Contract tests exist for broker/data adapter interfaces.

## Safety

- Every live order passes through the risk and execution lifecycle.
- Strategies and AI agents cannot bypass the risk engine through normal public APIs.
- Kill switch/safe mode exists as an explicit control.
- Order/fill/position discrepancies are auditable.
- Reconciliation failures fail closed for new live exposure.

## API and operations

- REST and WebSocket interfaces are versioned.
- CLI can inspect system status, strategies, positions, orders, and risk state.
- Health/readiness state exists for major adapters and services.
- Audit/event records have correlation identifiers.

## Research

- Backtests produce reproducible experiment metadata.
- Execution assumptions are explicit.
- Metrics and artifacts can be persisted.
- A strategy can move through draft/validated/backtested/paper/approved/live states without changing the underlying strategy definition.

## Quality

A v0.1 change is not considered complete unless applicable checks include:

```text
format/lint
unit tests
contract tests
integration tests
API tests
backtest smoke test
package/build validation
```

Architecture fitness tests must verify critical dependency rules such as core-to-plugin isolation and strategy-to-risk boundaries.

## Explicit non-goals for v0.1

The following are not required for v0.1:

- full visual Flow builder
- AI strategy generation
- complete multi-broker coverage
- cloud SaaS/multi-tenant deployment
- international market coverage
- advanced options analytics such as GEX/volatility surface
- every research library integration

These remain later milestones unless new evidence changes the priority.
