# QuantX v0.1 Build Order

Implementation follows dependency order, not feature popularity.

## Step 1 — Package and tooling

Establish Python packaging, supported Python version, linting, type checking, pytest, formatting, pre-commit hooks, and architecture tests.

## Step 2 — Domain primitives

Implement immutable/value-oriented primitives for UTC timestamps, money/currency, identifiers, instruments and contracts, plus domain errors.

## Step 3 — Event model

Implement domain events, event metadata, correlation/causation identifiers, in-memory message bus, and deterministic clock interfaces.

## Step 4 — Order/fill lifecycle

Implement order types, order state machine, fill model, idempotency keys, client order IDs, and invariant tests.

## Step 5 — Position/portfolio accounting

Implement positions, realized/unrealized P&L, portfolio state, and reconciliation boundaries. Keep broker state and local state explicitly distinct.

## Step 6 — Risk and policy layer

Implement risk policies, pre-trade checks, capital limits, position limits, trading-session checks, approval policy, and kill-switch interface.

## Step 7 — Execution port + paper broker

Define the broker/execution port and implement the paper adapter first. It must use the same order/fill semantics that future live adapters use.

## Step 8 — Strategy contract + Strategy IR

Implement the strategy interface, TradeIntent, Strategy IR v1, strategy registry, and a small reference strategy set.

## Step 9 — Runtime contexts

Implement backtest, deterministic replay, paper and live runtime boundaries. Backtest/paper/live share domain semantics; data source, clock and execution venue vary by context.

## Step 10 — Persistence and provenance

Add state/event persistence abstractions and research provenance. A backtest result must record strategy version, data version, engine version, parameters, execution model, fees/slippage model and seed where applicable.

## Step 11 — Reconciliation and recovery

Implement startup reconciliation, broker-state comparison interfaces, recovery state machine, retry/idempotency handling, and safe-mode startup rules.

## Step 12 — CLI and minimal API boundary

Only after the application services are stable, expose a small CLI and minimal REST/WebSocket contracts. UI is not part of v0.1.

## Step 13 — Contract/integration tests

Add adapter contract tests, end-to-end paper tests, restart/recovery tests, deterministic replay tests, and architecture fitness tests.

## Step 14 — v0.1 release gate

Pass the acceptance criteria in `docs/architecture/28-v0.1-acceptance-criteria.md`, then create the first release candidate.
