# QuantX v0.1 Build Order

Implementation follows dependency order, not feature popularity. This document is a build-order record, not a claim that every step remains incomplete.

## Step status

1. **Package and tooling — implemented.**
2. **Domain primitives — implemented foundation.**
3. **Event model — implemented where currently required; expand only for concrete use cases.**
4. **Order/fill lifecycle — implemented and actively hardened.**
5. **Position/portfolio accounting — implemented foundation.**
6. **Risk and policy layer — implemented foundation.**
7. **Execution port + paper execution — implemented foundation.**
8. **Strategy contract + Strategy IR — foundation exists; broader strategy platform remains future work.**
9. **Runtime contexts — replay/paper foundations exist; live runtime remains future work.**
10. **Persistence and provenance — SQLite-backed research, execution, and market-data persistence adapters exist, but that alone does not make the complete production deployment and integration lifecycle release-complete.**
11. **Reconciliation and recovery — active and substantially implemented; continuation and uncertain-submission recovery are current hardening areas.**
12. **CLI and minimal API boundary — future platform surface.**
13. **Contract/integration tests — substantial deterministic coverage exists and continues to expand.**
14. **v0.1 release gate — CLOSED for the declared programmatic local-first library scope (ADR-008); governed by `docs/architecture/28-v0.1-acceptance-criteria.md`.**

## Current implementation priorities

The items below remain release-critical non-regression invariants, not permission to reopen completed work without evidence:

1. execution lifecycle integrity;
2. uncertain-submission recovery;
3. continuation/recovery state correctness;
4. broker/account/position reconciliation;
5. deterministic research/replay integrity;
6. package-boundary consolidation only where a concrete duplication exists.

**Completed audit after R1-C14:** the v0.1 acceptance criteria were mapped against the existing process/runtime composition, and only proven local host, startup/readiness, configuration, shutdown, and integration-test gaps were closed — on exact local evidence, with no new CLI/server assumed or built.

Do not add UI, AI execution, distributed infrastructure, or a broad broker matrix merely because those features are in the long-term roadmap.

## Release gate

Acceptance for the declared programmatic local-first library scope (ADR-008) is complete once the canonical acceptance checklist in `docs/architecture/28-v0.1-acceptance-criteria.md` is satisfied with exact local evidence. That acceptance decision is distinct from three other things: the absence of a CLI, which is an explicit scope decision rather than a gap; the identification and validation of an exact candidate SHA whenever a release artifact is prepared; and any claim of real-broker end-to-end validation, production-broker certification, or production LIVE-readiness certification, none of which this checklist provides. GitHub Actions is not a validation gate while billing is disabled. An acceptance decision never automatically creates a packaged release or certifies live trading.
